# Working on Ariadne

Ariadne should read like a careful person explaining what a username scan can and cannot prove. Keep the interface useful before making it clever.

## Writing voice

- Read the surrounding copy before editing it. Keep the same calm, plainspoken tone.
- Prefer a concrete explanation over a polished slogan.
- Cut setup, filler and repeated caveats, but keep any caveat that changes what a result means.
- Do not turn uncertainty into confidence for smoother copy. “Maybe”, “Couldn’t tell”, “Blocked” and exact evidence have different meanings.
- Use contractions and short sentences when they sound natural. Do not add forced humor, slang or enthusiasm.
- Avoid stock product language such as “seamless”, “robust”, “comprehensive”, “unlock”, “empower”, “leveraging” and “designed to” unless it is genuinely the clearest wording.
- Never invent coverage claims, accuracy rates, user counts, community consensus or success metrics.

A good edit should make a sentence clearer, more specific or less repetitive. Do not rewrite text just to make it sound more polished.

## Evidence and safety

Public-page checks are not proof just because a page loads. Keep exact checks, broad checks and ambiguous responses visibly separate.

Do not add signup-form enumeration, password-reset probing, breach data, private APIs or authentication bypasses. Searches and friend comparisons should remain non-persistent unless the product explicitly changes that boundary.

## UI fit

For dense result screens, make sure long usernames, site names and evidence labels shrink or truncate without pushing controls out of their cards. Images/icons should remain centered and contained. Scrollable lists should not cause rows to jump when the scrollbar appears.

## Verification

Run the existing project checks for code changes. For copy/UI changes, also inspect the affected route at a normal desktop width and a narrow mobile width.
